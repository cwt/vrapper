# Bug 4 — Pending `imap` buffer (`cursorBeforeMapping`) erases autocompleted or inserted text

**Files:** [`DefaultEditorAdaptor.java`](../../plugins/net.sourceforge.vrapper.core/src/net/sourceforge/vrapper/vim/DefaultEditorAdaptor.java#L717-L780) [^src-1], [`KeyStrokeTranslator.java`](../../plugins/net.sourceforge.vrapper.core/src/net/sourceforge/vrapper/vim/KeyStrokeTranslator.java#L35-L78) [^src-2]
**Upstream Issues:** Related to [vrapper/vrapper#827](https://github.com/vrapper/vrapper/issues/827) and [vrapper/vrapper#889](https://github.com/vrapper/vrapper/issues/889)
**Severity:** HIGH (unexpected text deletion in Insert mode)

## Description

In `DefaultEditorAdaptor.handleKey0(KeyStroke key)`, when `currentMode instanceof InsertMode` and the user presses a key that starts a multi-character `imap` (e.g., `:imap ii <Esc>` or `:imap jj <Esc>`):

1. `cursorBeforeMapping` is set to `cursorService.getPosition().getModelOffset()` and the pending character is inserted into Eclipse (`resultingKeyStrokes.isEmpty()`).
2. If Eclipse Content Assist activates before the mapping finishes (`ContentAssistMode` resolves `"Content Assist Mode Keymap"` rather than `"Insert Mode Keymap"`), or if autocomplete / LinkedMode / mouse movement inserts text and moves the cursor forward, `keyStrokeTranslator` is **not** reset and `cursorBeforeMapping` retains the old offset.
3. Upon returning to `InsertMode` and completing or backtracking the mapping (`didMappingSucceed || doBackTrack`):

```java
int pendingChars = cursorService.getPosition().getModelOffset() - cursorBeforeMapping;
for (int i = 0; i < pendingChars; i++) {
    currentMode.handleKey(new RemappedKeyStroke(new SimpleKeyStroke(SpecialKey.BACKSPACE), false));
}
```

Vrapper computes `pendingChars` as the raw offset delta and deletes all text inserted since `cursorBeforeMapping` (not just the pending mapping prefix). Conversely, if the cursor moved backward, `pendingChars <= 0` and the pending prefix is never removed.

## Impact

- Any text inserted by Eclipse autocomplete, templates, or manual cursor movement while an `imap` prefix is pending can be silently erased when the mapping completes or backtracks.

## Resolution

Added `KeyStrokeTranslator.reset()` ([`KeyStrokeTranslator.java`](../../plugins/net.sourceforge.vrapper.core/src/net/sourceforge/vrapper/vim/KeyStrokeTranslator.java#L37-L44)) [^src-2], exposed `EditorAdaptor.resetPendingMapping()` (`DefaultEditorAdaptor.changeMode` and `InsertMode.resetEditingSession()` both call it so mode switches such as `ContentAssistMode`/`InsertExpandMode` and arrow/mouse resets clear any in-progress mapping), and updated [`DefaultEditorAdaptor.java`](../../plugins/net.sourceforge.vrapper.core/src/net/sourceforge/vrapper/vim/DefaultEditorAdaptor.java#L714-L855) [^src-1] to track `pendingInsertKeys`, validate that the buffer text and offset still match pending chars before continuing an `imap` sequence, and cap deletion to the tracked pending keys. Added 4 regression tests in [`InsertModeTests.java`](../../tests/net.sourceforge.vrapper.core.tests/src/net/sourceforge/vrapper/core/tests/cases/InsertModeTests.java#L104-L176). Verified via `mvn -B clean verify --file pom.xml` (`318` run, `0` failures, `0` errors, `2` pre-existing `@Ignore` skipped in `core.tests`; `6/6` in `surround.tests`).

**Status:** FIXED.
